01What the system is

A voice assistant for a college. You speak; it decides which of five skills can answer; it runs that skill; it speaks a short answer back. Signed in as a student it answers about you and can see nobody else's records.

Every component runs locally except the language model, which uses NVIDIA NIM's free tier. No paid API, no credit card.

03Speech to text — faster-whisper

app/stt.py · model base, int8, CPU

How Whisper works

Whisper is an encoder-decoder Transformer trained on 680,000 hours of labelled audio.

  1. Audio is resampled to 16 kHz mono.
  2. It becomes a log-Mel spectrogram — a 2-D picture of energy across 80 frequency bands over time. This is the model input; Whisper never sees raw samples.
  3. The encoder turns that spectrogram into a sequence of vectors.
  4. The decoder generates text tokens autoregressively, cross-attending to the encoder output — the same architecture as a translation model, with audio on one side and text on the other.
  5. Special tokens at the start select the task: language, transcribe-vs-translate, timestamps. This is why language detection is free — the model predicts a language token before any text.

Why faster-whisper rather than openai-whisper

A reimplementation on CTranslate2, a C++ inference engine. Same weights, different runtime:

  • Quantisation — int8 stores weights as 8-bit integers instead of 32-bit floats: ~4× smaller and faster on CPU, because integer arithmetic is cheaper and far more of the model fits in cache. Accuracy loss on base is small.
  • Layer fusion and a custom attention kernel, rather than PyTorch's generic operator dispatch.
  • No PyTorch at inference time.

Typically 3–4× faster than the reference implementation on CPU at equal output.

The weakest link in the system

Real transcripts from testing: "and that my CG that make my CGP off" for "what's my CGPA", and "I got 30 months right" for "I got 30 marks". No prompt engineering recovers from that.

Two mitigations ship: the edit & resend link under every voice question, and garbled clarifications now routing to smalltalk rather than inventing a database query. Moving to small is a one-line change in config.py.

Alternatives rejected

  • Google / Azure / AWS speech — accurate and fast, but paid, needs a card, and sends audio off-device. The brief required free and local.
  • Vosk — genuinely offline and light, but noticeably worse on accented English.
  • Web Speech API — free and zero install, but Chrome silently ships audio to Google's servers, Firefox lacks it, and it cannot be demoed offline.

04The language model — NVIDIA NIM

app/llm.py

What NIM is, and why the openai package

NVIDIA NIM exposes models behind an OpenAI-compatible REST API. Because the wire format matches, the official openai package works as a client with only the base URL changed:

OpenAI(base_url="https://integrate.api.nvidia.com/v1", api_key=NVIDIA_API_KEY)

No OpenAI account or key is involved. The package is a well-tested HTTP client for a protocol NVIDIA happens to implement. Hand-rolling requests calls would mean reimplementing streaming, retries and error types for no benefit.

Three models, chosen by measurement

SettingModelJob
LLM_MODELllama-3.1-70b-instructwrites SQL
ROUTER_MODELllama-3.1-8b-instructpicks the skill
COMPOSE_MODELllama-3.1-8b-instructwrites the spoken answer

This split came from data. Eight identical calls, same prompt, same token limit:

ModelLatency across 8 calls
8b0.41, 0.47, 0.41, 0.47, 0.50, 0.44, 0.46, 0.48 — flat
70b2.40, 25.19, 3.59, 18.27, 2.72, 1.28, 0.94, 24.15

The free-tier 70B endpoint is queue-contended. So the two easy jobs — a 5-way classification and a short rewrite of data already computed — went to 8B, which is both faster and more predictable.

But SQL stayed on 70B, because accuracy mattered more:

AccuracyMedianMax
70B11/1142.5s132.6s
8B8–10/110.78s1.02s

8B scored 6/6 in isolation but degraded in a real conversation, flaking on "lowest attendance" (a LEFT JOIN NULL-ordering trap) and on normalising percentages. Setting LLM_MODEL = ROUTER_MODEL flips the whole system to fast-and-flakier.

A model being listed does not mean it works

meta/llama-3.3-70b-instruct appears in NIM's /v1/models but every inference request hung until timeout. Diagnosis: a deliberately wrong key returned 403 in 0.4s — proving network and auth were fine — while 3.1-70B answered the identical request in 0.6s. Always test the exact model string.

Why not a "thinking" model

R1-style models emit chain-of-thought before the answer. This system parses strict JSON from the router and bare SQL from the generator. Reasoning traces break both parsers.

Reliability wrapper

llm.chat() never raises. On failure it returns "" and the caller falls back:

  • 429 rate limit → exponential backoff, 2s → 4s → 8s (free tier is ~40 requests/minute; each question costs 2–3 calls).
  • JSON parsing → strip fences, json.loads, then regex out the first {...}, then a caller-supplied fallback.
  • Streaming retries only before the first token. Once text has been handed to the caller it cannot be unsaid, so a mid-stream break ends the stream rather than restarting and duplicating output.

05Routing

app/router.py — one LLM call classifies into one of five skills and returns strict JSON: {"tool": "...", "reason": "..."}. The reason is shown in the UI.

ApproachWhy not
Keyword rules"How many students are in semester 6" and "What is the attendance policy" share the word attendance. Rules become an unmaintainable thicket and fail on paraphrase.
Embedding similarity to skill descriptionsCheap and local, but poor at intent. "Remind me about the attendance policy" is lexically close to both reminders and documents.
Fine-tuned classifierBest accuracy, but needs a labelled dataset that does not exist for a student project.
LLM with a JSON contract ✓Handles paraphrase and context, needs no training data, and the reason field doubles as a UI explanation. Measured 9/9 on the routing test set.

Defensive parsing

The router must not be able to crash the app. Parsing is layered: strip fences → json.loads → regex-extract the first JSON object → validate the tool name against a whitelist → fall back to search_documents.

Conversation-aware routing

A clarification like "is that a percentage or a CGPA?" is answerable by re-reading the previous turn. It used to hit the database and generate SELECT 'percentage' — a fabricated query. Those now route to smalltalk, which sees the history and repeats the figure it already gave rather than recomputing a different one.

06Text to SQL

                │                        │

Prompt construction

The system prompt is built at runtime from the live database, so it cannot drift:

  1. CREATE TABLE statements read from sqlite_master.
  2. Three sample rows per table — so the model sees that exam_type is 'midterm', not 'mid-term'.
  3. Every value of low-cardinality columns (subject names, branches, exam types) so it matches exact spellings instead of guessing LIKE patterns.
  4. Derived views for grades, with sample rows.

Grades and CGPA — derived, not guessed

The bug

Asked "what is my CGPA?", the model averaged mark percentages and answered "your CGPA is 74.4". A percentage is out of 100; a CGPA is out of 10. Confidently wrong.

The grading rules are published in docs/exam_grading_policy.md, so they can be computed exactly. Three temp views do it:

subject_totals  → weight each exam type (quiz 20, midterm 30, final 50),
                  rescaled to 100 over the components actually present
subject_grades  → grade bands O=10 … F=0
cgpa            → SUM(grade_points × credits) / SUM(credits)

Verified against a hand calculation:

SubjectTotalGradePointsCredits
Artificial Intelligence97.0O103
Compiler Design67.2C74
Computer Networks55.5D63

CGPA = (10×3 + 7×4 + 6×3) / 10 = 7.6 — matching exactly. The rescaling matters: only components a student actually has are counted, so a missing quiz does not silently drag the grade down.

07Retrieval over documents — RAG

app/rag_tool.py

ApproachWhy not
All policies in the promptWorks at 3 documents but does not scale, and wastes tokens on every call.
Fine-tune on the policiesExpensive, needs retraining whenever a rule changes, and still hallucinates specifics.
Keyword searchFails on paraphrase: "how much do I have to attend" never matches "minimum attendance requirement".
Embed + nearest neighbour ✓Handles paraphrase, updates by re-ingesting a file, grounds the answer in quotable text.

How embeddings work

all-MiniLM-L6-v2 is a 6-layer Transformer producing a 384-dimension vector per text. It was trained so semantically similar sentences land close together — contrastive training on ~1B sentence pairs, pulling true pairs together and pushing random pairs apart.

Vectors are normalised to unit length, which makes cosine similarity equal the dot product — so "similarity" is just an angle between two directions in 384-D space.

Why MiniLM: 22M parameters, ~90MB, milliseconds on CPU. Larger models (all-mpnet-base-v2, 110M) score a few points higher but are ~5× slower — a bad trade when the point is a responsive voice loop.

Chunking

500 characters with 50 characters of overlap, snapped backwards to the nearest space so words are never cut in half.

  • Too large → the embedding averages several topics and matches nothing well.
  • Too small → context is lost mid-sentence.
  • Overlap exists so a fact sitting on a boundary appears whole in one chunk.

3 documents → 17 chunks.

ChromaDB and HNSW

Chroma stores vectors and metadata and does nearest-neighbour search using HNSW (Hierarchical Navigable Small World) — a layered graph where each node links to its neighbours. Search starts in a sparse top layer, greedily walks toward the query, then drops a layer and refines. That gives approximate nearest neighbours in O(log n) instead of comparing against every vector.

At 17 chunks this is irrelevant — a brute-force NumPy loop would be just as fast. Chroma earns its place by handling persistence, metadata and the API so the code stays small, and by not needing a rewrite if the corpus grows.

The confidence floor

Retrieval always returns something

An off-topic question was measured pulling chunks at 0.19 similarity, which the composer would then dutifully answer from. RAG_MIN_SCORE = 0.25 drops those, so "Who won the football world cup in 1998?" returns 0 chunks and an honest "I couldn't find anything about that."

08The other three skills

Timetable

No generated SQL. The shapes of timetable questions are few and fixed, so the queries are hand-written and parameterised: faster, free, impossible to get wrong. The LLM only classifies which day is being asked about, falling back to "today".

"Next class" walks forward from now through teaching days until it finds one that has not started yet.

Reminders — the only skill that writes

model output:  {"action":"add", "text":"submit the AI assignment", "due":"friday"}
                            │
                   Python parses the date
                            │
INSERT INTO reminders (student_id, text, due_date, created_at, done)
VALUES (?, ?, ?, ?, 0)          ← fixed statement, bound parameters

There is no path from model output to a write statement. The text-to-SQL tool keeps its read-only connection and all nine guards. Tests assert the validator still rejects INSERT INTO reminders and that the read-only connection still raises on writing to it.

Smalltalk

Greetings, "what can you do?", out-of-scope questions, and clarifications about the previous answer. Before this route existed, "hello" was forced into document search and answered from irrelevant policy text.

09Answer composition

app/compose.py

Raw rows are never spoken — name | avg_percent read aloud is meaningless. Every result passes through a final LLM call producing 1–2 plain sentences, with markdown stripped defensively afterwards.

The style prompt encodes rules that exist because the model got them wrong:

  • Round to one decimal. It once said "74.42857142857143 percent".
  • A mark needs its total and subject — "30 out of 50 in Computer Networks", never a bare "30".
  • Only claim a tie when numbers are exactly equal, with worked examples of tied vs merely ranked.
  • Use names or "they", never "he"/"she".

The access rule

When the caller is a student, an extra block is added to the system prompt (not the user turn — system instructions are followed far more reliably). It draws a line between:

  • about themselves → answer fully, including their own totals and averages
  • needs anyone else's data → refuse, then offer their own figure
This needed two iterations

The first wording said "an average across students", which the model over-generalised to any average — so "what is my overall percentage?" started getting refused. There are now tests asserting the rule still permits personal totals.

10Text to speech — pyttsx3

app/tts.py

pyttsx3 drives the operating system's own speech engine: SAPI5 on Windows, NSSpeechSynthesizer on macOS, espeak on Linux. Offline, free, no API.

Concurrency, the interesting part

SAPI5 is a COM interface, and COM is apartment-threaded — objects belong to the thread that created them. A long-lived engine shared across a web server's worker threads is unreliable. So every synthesis runs on a fresh short-lived thread that calls CoInitialize() itself, guarded by a lock so two voices never overlap.

OptionWhy not
ElevenLabs / Azure TTSFar better voices, but paid and online.
PiperGenuinely good neural TTS, offline, free. Heavier install and per-voice model downloads. The interface is built for it — implement synthesize(), register in _ENGINES, set TTS_ENGINE=piper.
Browser speechSynthesisFree and zero install, but quality varies wildly by browser and the server cannot produce audio for a non-browser client.
pyttsx3 ✓Works out of the box on Windows with no downloads. Robotic, but the brief prioritised "runs after one pip install".

11Authentication

app/auth.py

Passwords — bcrypt

bcrypt is a deliberately slow hash built on the Blowfish key schedule. Its cost factor sets how many iterations run; raising it by one doubles the work. The point is that hashing must be expensive enough to make offline brute-force impractical, while still being milliseconds for one login.

Each hash embeds a random salt, so two users with the same password get different hashes and rainbow tables are useless. There is a test asserting exactly that.

Passwords over 72 bytes are rejected, because bcrypt silently truncates there — a longer password would be weaker than it looks.

AlternativeNote
SHA-256Catastrophic for passwords — designed to be fast, so brute-force is cheap.
PBKDF2Fine, in the standard library, but not memory-hard.
scrypt / Argon2idMemory-hard, arguably better; Argon2id is the modern recommendation. bcrypt was chosen as the most universally recognised battle-tested option. Either is a defensible upgrade.

Sessions — JWT

A JWT is three base64url parts: header.payload.signature. The signature is HMAC-SHA256 over the first two using a server secret, so the payload is readable by anyone but not forgeable without the key.

Claims used: sub (user id), role, tv (token version), iat, exp.

Logout is the interesting bit

JWTs are stateless, so a plain token cannot be revoked before it expires. Here every user row carries a token_version, and the token carries a copy. Logging out increments the column, so every outstanding token for that user fails its next check — real revocation without a denylist table that grows forever.

The honest trade-off

A JWT in sessionStorage is readable by any successful XSS, which an HttpOnly cookie would not be. JWT was chosen deliberately after that was flagged. Mitigations shipped: sessionStorage (per-tab, cleared on close), 60-minute expiry, real revocation, a strict CSP, and zero third-party scripts. For production, cookies are the safer default.

Other guards

  • No user enumeration — unknown username and wrong password return the identical message. A test asserts the strings are equal.
  • Lockout — 5 failures locks the account for 15 minutes, correct password included.
  • Signup claims a seeded record — the roll number must exist, the name must match (case- and whitespace-insensitive), and it must not already be claimed. student_id is UNIQUE, so the database enforces the last one too.

12Row-level security

The most technically interesting part of the project

The model chooses the SQL, so "don't look at other students" cannot be a prompt instruction — it has to be enforced where the data lives.

The mechanism

SQLite resolves unqualified table names against the temp schema before main. So creating a temp view with the same name as a table shadows it for that connection:

CREATE TEMP VIEW marks AS SELECT * FROM main.marks WHERE student_id = 20;

Every ordinary SELECT ... FROM marks now sees one student. Measured on the real database with the same query text:

QueryAs staffAs student 20
SELECT COUNT(*) FROM students301
SELECT COUNT(*) FROM marks1507
SELECT COUNT(*) FROM attendance2009
"rank everyone by average"all 30only themselves

Live through the API, with identical generated SQL in both cases:

"Who has the lowest attendance?"

student   "I can only show you your own records. Your attendance is 100 percent."

staff   "Pooja Joshi has the lowest attendance at 25 percent."

Three details that make it actually hold

  1. main. is rejected by the validator. A temp view is bypassed entirely by SELECT * FROM main.marks, which returns all 150 rows. This was found during planning and is the single most important line in the security model — without it the views are decorative.
  2. The credentials table is blanked on every connection, staff included, and excluded from the schema dump. Otherwise schema_context() would paste password hashes into the prompt and into the UI panel.
  3. Prompt sample rows come from the scoped connection. An unscoped dump would leak other students' names to the model even when the query itself was correctly restricted.
AlternativeWhy not
Prompt instructionTrivially bypassed. Indefensible in review.
Rewrite the SQL to inject WHERE student_id = ?Requires parsing SQL correctly, including subqueries and joins. Fragile.
A separate database per studentCorrect but absurd at any scale.

A regression here fails silently — the assistant keeps answering, it just answers with somebody else's data. tests/test_rls.py runs the adversarial queries as a student and asserts only their own rows come back.

13The web layer — FastAPI + uvicorn

AlternativeWhy not
FlaskFine and familiar, but sync by default and needs extra libraries for validation and streaming.
DjangoAn ORM, admin and migrations this project does not need.
FastAPI ✓Type-hint-driven validation (Pydantic rejects malformed requests before any handler runs), native async, and StreamingResponse for NDJSON — all in the standard install.

uvicorn is the ASGI server that actually speaks HTTP. Note: uvicorn plain, not uvicorn[standard] — the extras pull in httptools and uvloop, which need a C compiler on some platforms and buy nothing here. That was a real install failure before it was changed.

Speculative execution

The router and the tools used to run in sequence, so the SQL generator sat idle waiting for a routing decision. Now the router, the SQL tool and RAG retrieval all start together on a shared thread pool; when the router decides, the loser is abandoned.

A subtle detail

The pool is deliberately not a context manager — with ThreadPoolExecutor() blocks on exit until every future finishes, which would defeat the entire purpose.

Cost: one wasted SQL-generation call whenever the router picks documents. SPECULATIVE_TOOLS = False disables it if you are near the rate limit.

14The frontend

One file, static/index.html — markup, CSS and JS together, no build step. That is not laziness: it means no bundler, no node_modules, no CDN, and a strict Content-Security-Policy (default-src 'self') costs nothing.

MediaRecorder

getUserMedia opens the microphone; MediaRecorder encodes to WebM/Opus in the background and hands back Blob chunks. Opus is a modern low-latency codec — a few seconds of speech is tens of kilobytes. faster-whisper decodes WebM through PyAV (FFmpeg bindings), so no explicit conversion step is needed.

Web Audio API and the orb

AudioContext → AnalyserNode gives real-time samples. getByteTimeDomainData fills a buffer with the waveform, from which peak amplitude is computed every 60ms.

That single number drives the orb. Two sources feed it: the microphone while recording, and a MediaElementSource tapped off the <audio> element while the assistant speaks — without the second, the orb goes dead exactly when the assistant is talking.

The orb itself is <canvas>: three rotating rings whose radius is base + sin(a·3 + t)·k + sin(a·5 − t·1.3)·k2. Two out-of-phase sines make it bulge organically rather than pulse as a perfect circle. The level is eased (shown += (target − shown) × 0.18) so it glides instead of jittering.

SQL highlighting

About 20 lines of regex, no library. The order matters:

  1. escape HTML first (&, <, >, quotes)
  2. pull quoted literals out to placeholders, so a keyword inside 'Artificial Intelligence' is not recoloured
  3. wrap keywords, functions, numbers
  4. restore the literals
Why it is tested

This is the only place the app writes innerHTML, and it renders LLM-generated text. It is tested directly, including SELECT '<img src=x onerror=alert(1)>', which comes out escaped. A pytest guard asserts every other innerHTML write is a constant.

Theming

Light and dark are a token swap. Because every surface reads from CSS custom properties, the light theme redefines ~20 variables rather than duplicating the stylesheet. Follows the OS by default, remembers a manual choice in localStorage. The orb needs its own palette per theme — a canvas cannot inherit CSS colours.

15Conversation memory

app/memory.py — the last 6 turns per account, in process, so "and what about semester 4?" resolves against the previous question.

  • Keyed by authenticated account, never by a client-supplied string. The original design took a session_id from the browser — anyone could send anyone else's id and read their history.
  • The SQL prompt sees only 2 turns, not 6. A long history stapled onto a text-to-SQL prompt measurably degrades accuracy on smaller models: they start answering the earlier question.
  • Idle sessions are evicted after 2 hours with a hard cap of 500 — without that, every browser that ever loaded the page leaked a buffer for the process lifetime.

Three principles worth defending

  1. Every bug found got a test. The list in §18 maps one-to-one onto tests.
  2. Tests verify against independent implementations, not themselves. test_skills.py re-implements the grading policy in Python and asserts the SQL views agree — a bug would have to be made identically twice.
  3. Guards are proven to fail. After adding the [hidden] CSS fix, the guard was run against the broken stylesheet to confirm it fails. A test that passes either way is worthless.

Two meta-lessons

A whole class of bug was invisible to both test layers. The JS harness executes the script without CSS; pytest never opens a browser. The login bug passed everything and still looked completely broken. That gap is why test_frontend.py exists.

Prompts can poison themselves. The composer prompt literally contained "if it says the user needs to sign in, tell them that" — which primed the model to say it to a signed-in student with a perfectly good timetable.

19Honest limitations

Worth stating plainly rather than being caught out.

  • Whisper base mishears often. The single biggest quality limit. small is a one-line change at ~3× the time.
  • The 70B endpoint is unpredictable on the free tier — occasional 30s turns.
  • JWT in sessionStorage is XSS-readable. A deliberate, documented choice; cookies are safer.
  • Signup is not identity proofing. Roll number + matching name is a demo-grade check.
  • Single-process memory. Conversation history dies on restart and does not survive multiple workers.
  • Hindi is claimed, not verified. The hardcoded language="en" was removed and auto-detection added, but it was never tested with real Hindi speech.
  • Hands-free was removed. The server-side wake gating worked (verified with synthesized speech); the browser-side voice-activity detection was never tuned against a real microphone in a real room.
  • Docker is written but unbuilt — Docker was unavailable in the development environment.
